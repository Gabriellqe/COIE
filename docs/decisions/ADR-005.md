# ADR-005 — Autenticación e aislamiento mediante espacios de trabajo

## Contexto

El MVP tendrá entre tres y cuatro usuarios. Cada persona necesita datos aislados, aunque en el futuro podrá colaborar en un espacio compartido. Una base física por usuario complicaría migraciones y operación.

## Decisión

- Usar Supabase Auth con correo y contraseña, sin MFA obligatorio en el MVP.
- Mantener una única base PostgreSQL.
- Crear `Workspace` y `WorkspaceMember`.
- Toda entidad comercial propiedad de usuarios incluye `workspace_id`.
- Aplicar Row Level Security al integrar Supabase, verificando membresía antes de leer o modificar datos.
- Crear inicialmente un espacio personal por usuario; los espacios compartidos se habilitarán sin cambiar el modelo.

Un login sencillo no reduce el requisito de aislamiento entre usuarios.

## Alternativas consideradas

### Base física por usuario

Descartada por costo operativo y dificultad para colaboración, migraciones y análisis.

### Aplicación sin autenticación

Descartada porque contradice el uso multiusuario definido para el MVP.

### Autenticación propia

Descartada para evitar almacenar contraseñas o implementar seguridad de identidad desde cero.

## Consecuencias

- El fixture y los contratos incluyen `workspace_id` desde Foundation.
- La autenticación real queda pendiente hasta crear el proyecto Supabase.
- Las pruebas futuras deben comprobar acceso cruzado denegado.

## Criterio de revisión

Revisar si el producto requiere SSO, MFA, roles administrativos o aislamiento físico por regulación.
