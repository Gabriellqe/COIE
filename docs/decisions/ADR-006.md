# ADR-006 — Opportunity como agregado central y perfil MVP-A Resale

## Contexto

La revisión de las síntesis históricas del proyecto confirmó que COIE creció a partir de varias capacidades relacionadas, pero todas buscaban resolver un único problema: convertir una hipótesis comercial en una oportunidad evaluada, probada y aprendida.

La documentación vigente preservaba las capacidades, aunque presentaba tres ambigüedades:

- `Opportunity` estaba conceptualmente generalizada, pero el flujo y el modelo efectivo eran product-centric;
- `RESALE` y `REPLENISHMENT` se denominaban conjuntamente «MVP» pese a depender de incrementos distintos;
- Experimentation era central en la visión, pero estaba situada después de varios módulos no necesarios para validar el primer ciclo.

## Decisión

### Modelo operativo

COIE se organiza alrededor de `Opportunity` y del ciclo:

```text
DISCOVER → EVALUATE → TEST → MEASURE → SCALE / REJECT / MODIFY
```

Toda evolución debe ayudar a responder cinco preguntas:

1. ¿Qué vender?
2. ¿Vale la pena?
3. ¿Dónde comprarlo?
4. ¿Cómo venderlo?
5. ¿Debería seguir haciéndolo?

Se distinguen tres dimensiones:

```text
Opportunity
├── Strategy: RESALE | REPLENISHMENT | IMPORT | ARBITRAGE | ...
├── Subject: LISTING | PRODUCT | NICHE | SUPPLY_ROUTE | PRODUCT_SET
└── Capabilities: Market, Pricing, Economics, Risk, Experimentation, ...
```

Las estrategias no son aplicaciones independientes y las capacidades no son tipos de oportunidad. Todas enriquecen una misma `Opportunity`.

### Perfil implementado

El primer vertical se denomina **MVP-A Resale Decision** y admite únicamente:

- estrategia `RESALE`;
- sujeto efectivo `PRODUCT`, respaldado por una o más publicaciones;
- Chile/CLP como mercado de validación;
- carga manual trazable y datos DEMO mientras no exista una fuente real permitida.

El contrato Foundation vigente conserva `opportunityType` y `productId`. Es un perfil parcial, no el modelo objetivo completo. La generalización nativa a `strategy + subject` exigirá una nueva versión de esquema y una migración explícita; no reinterpretará silenciosamente datasets `0.1.0`.

### Alcance MVP-A

MVP-A se entrega en tres incrementos:

1. **A1 — Market Evidence:** identidad, comparables y estimación trazable de precios observados.
2. **A2 — Resale Decision:** pricing comercial, precio máximo de compra, economía básica, riesgo, confianza, gates y decisión humana.
3. **A3 — Experimentation Lite:** predicción congelada, prueba acotada, medición y decisión.

`Economics Core` acepta costos manuales en A2. `Sourcing Intelligence` completo, `REPLENISHMENT`, nichos, relaciones de catálogo, estacionalidad, aprendizaje y descubrimiento autónomo pertenecen a incrementos posteriores.

### Estados y resultados

La máquina operativa mantiene los estados vigentes:

```text
DISCOVERED → RESEARCHING → SHORTLISTED → TESTING → VALIDATED → SCALING
                         ↘ REJECTED
```

Un experimento `INCONCLUSIVE` o una decisión `MODIFY` devuelve la oportunidad a `RESEARCHING` con nueva evidencia, hipótesis o versión; no se cuenta como validación ni rechazo definitivo.

## Relación con decisiones anteriores

- Conserva la decisión principal de [[ADR-001]]: Resale Intelligence es un módulo de COIE.
- Reemplaza únicamente la cláusula de alcance que situaba `RESALE` y `REPLENISHMENT` juntos en el MVP.
- Conserva mercado, adquisición y stack de [[ADR-002]], [[ADR-003]] y [[ADR-004]].

## Alternativas consideradas

### Construir todos los tipos sobre un sujeto polimórfico ahora

Descartada porque aumentaría el alcance de Foundation sin validar el primer flujo comercial.

### Mantener `RESALE + REPLENISHMENT` como un único MVP

Descartada porque mezcla hipótesis, señales y contratos diferentes antes de completar el ciclo más simple.

### Entregar sólo estadísticas de precio

Descartada porque no valida la propuesta de decisión y aprendizaje que originó COIE.

## Consecuencias

### Positivas

- restaura un hilo conductor único;
- reduce el primer alcance sin perder la visión;
- permite validar el ciclo completo antes de añadir módulos;
- distingue modelo objetivo y perfil ejecutable.

### Costos y riesgos

- requiere reestructurar PRD, roadmap, backlog y contratos documentales;
- los tipos futuros no serán ejecutables todavía;
- la transición a sujetos múltiples necesitará migración versionada.

## Criterio de revisión

Revisar cuando MVP-A complete al menos un experimento real o cuando una oportunidad no basada en producto esté lista para implementación.
